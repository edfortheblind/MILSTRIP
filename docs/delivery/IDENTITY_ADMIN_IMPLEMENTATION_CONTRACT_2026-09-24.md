# Identity and administration implementation contract

**Date:** September 24, 2026

**Status:** Implemented in source; native deployment and acceptance pending

Implements [ADR 0006](../adr/0006-user-identity-and-administration.md). Existing
app IDs, solution, custom connector and gateway remain. This contract defines
the boundary between backend, control-state and canvas/flow work.

The [delivery status](IDENTITY_ADMIN_STATUS_2026-09-24.md) records current tenant
evidence separately from source validation. Licensing is resolved in both
published players; Stage is healthy and Prod remains disabled pending its target
decision. All six initial directory members were verified enabled and internal.

## 1. Broker transport

Add `POST /api/v1/broker/invoke`, operation ID **InvokeBroker**, to the existing
connector. Require a private flow-owned Basic credential with a fixed tenant and
profile binding, and retain the loopback peer restriction. Broker credentials
must never be embedded in a canvas data source or shared with its viewers.

Use an OpenAPI 2-compatible fixed envelope:

```json
{
  "schema_version": 1,
  "request_id": "<UUID generated by the flow>",
  "actor": {
    "object_id": "<invoker profile object ID>",
    "upn": "<invoker profile UPN>",
    "display_name": "<trusted directory display name>",
    "account_enabled": true,
    "user_type": "Member"
  },
  "operation": "GetCurrentUser",
  "payload_json": "{}"
}
```

Only the flow constructs `actor`. Tenant/profile come from the authenticated
broker binding, never client data. The flow obtains identity with invoker-owned
Office 365 Users **Get my profile (V2)**. Resolve new membership targets using a
separate trusted directory connection fixed to the expected tenant. The required
enabled-account and internal-member evidence is flow-generated, not copied from
the app. Do not use raw trigger headers as an identity fallback.
The flow must reject an external or disabled caller before invoking the API;
request the required profile fields explicitly and fail closed if directory
verification is unavailable. The API independently requires an active ACL entry
for that object ID and the configured tenant, and validates the corporate UPN
domain as an additional restriction, never as a substitute for the ACL.

`payload_json` is a transport accommodation for the current connector exporter;
parse it once into a strict model selected by `operation`, reject unknown fields,
and impose explicit size bounds. No dynamic invocation or HTTP proxying.

Return `{request_id, result_json}` on success. Use actual HTTP 401/403/409/422/503
for API failures with `{request_id, code, message}` containing safe diagnostics.
The flow catches them and returns a stable canvas envelope:
`{ok, status, request_id, result_json, error_code, error_message}`. Transport
timeouts remain unknown outcomes; do not translate them into a failed commit.

## 2. Operation and capability map

| Operation | Required capability | Business database required |
|---|---|---|
| GetCurrentUser | Active verified membership | No |
| GetHealth | Active verified membership | Probe only; disabled is a valid response |
| ListIntakeRequests, GetIntakeRequest, ListRecordResults, ListAuditEvents | business | Yes |
| CreateIntakeRequest, CreateReviewDecision | business | Yes |
| ListUsers, SaveUserAccess | users.manage | No |
| GetRuntimeProfiles, SaveRuntimeDraft, TestRuntimeDraft, ApplyRuntimeDraft | runtime.configure | No current target required |
| GetAdministrationOperation | Initiator or corresponding management capability | No |

Owner and Admin possess all three capabilities. Operator possesses `business`.
Enforce fixed owner identities in every ACL mutation path, not only in canvas.
Do not permit assigning Owner through `SaveUserAccess`. Profile mutation targets
must match the broker-bound app environment. All ACL and configuration reads
must work when the selected business profile is disabled or unreachable.

Retain current business request/result models and commit semantics. Store the
verified tenant/object ID as the human audit identity, with display metadata and
broker identity separately. Do not rewrite historical shared-account actors.
After the enforced cutover, the old seven HTTP routes either require an already
verified internal principal or reject direct use; possession of legacy Basic
credentials alone never authorizes business operations.

## 4. Administration state and configuration commands

Use one independent `.cred/control.json` with atomic writes under one lock and
compare-and-swap revisions. Keep ACL and administration accessible regardless of
business database health. Import legacy runtime settings once, preserving both
profiles and credentials; do not leave a second active configuration authority.

`SaveRuntimeDraft` accepts expected revision, provider, safe label, enabled state
and an optional write-only replacement string. A blank replacement means retain
the saved string; provider changes require a replacement. Saved secrets never
appear in results, audit events or exception messages.

`TestRuntimeDraft` performs existing read-only connectivity, six-table column and
environment-marker checks. Persist a test receipt tied to draft digest, profile,
active revision, actor and expiry. No DDL or business writes. Missing schema is
a provisioning requirement, not an invitation to auto-create it.

`ApplyRuntimeDraft` carries a command UUID, expected active revision and test
receipt ID. Recheck the current role and receipt; drain only the affected profile,
commit the new durable active revision and release new requests onto it. Timeout
or failed validation retains the old active revision. Recover the committed
revision after process restart. `GetAdministrationOperation` resolves an unknown
result without repeating a change under a new command ID. Concurrent edits yield
409. The control-state implementer owns the precise lease/durability protocol.

Reject changing an enabled profile's normalized database target with HTTP 409
`CONFLICT` and a disable-first message. Disable and drain it first; disabling needs
no successful database test. Keep it disabled during separate data migration and
reconciliation, then test and apply the new target. Same-target credential or
label changes may use a brief drain. The other app remains available. No cross-
database fallback is permitted. Require one API worker and make this service
the sole writer of active state while serving; native tools/CLI cannot bypass
the registry. Crash recovery follows the durable active revision and recorded
operation result, never an uncommitted in-memory candidate.

## 5. Membership and platform-sharing reconciliation

`SaveUserAccess` accepts a command UUID, expected ACL revision, desired Admin or
Operator role, active state and a directory-verified target when adding access.
Removal accepts a normalized `target_upn` instead: the API resolves one existing
membership and uses its stored object ID, including after directory deletion or
disablement. It cannot create a new identity through this path. Do not trust a raw
object ID/email from canvas as directory verification. Store a bounded platform
sharing plan for the fixed two app IDs and two broker flow IDs. Desired ACL and
observed platform permissions are separate fields.

The controlled flow uses private management connections for these documented
operations:

- Power Apps for Makers: `Get-AppRoleAssignment`, `Edit-AppRoleAssignment`.
- Power Automate Management: `ListFlowUsers`, `ModifyRunOnlyUsers`.

Use individual **CanView** app grants and **run-only** flow grants for the six
initial members. Never grant CanEdit, CanViewWithShare, flow ownership or maker
roles because somebody is an application Admin or Owner. Existing legitimate
deployment ownership is separate and must not be stripped automatically.
The explicitly verified deployment Owner, Ed, is the sole exception to exact
CanView readback: his existing Owner grant already permits viewing and is not
edited. His application role remains Admin. Application removal denies API use,
but platform cleanup requires IT ownership transfer before it can complete.
Never use Everyone or tenant-wide sharing. The flow account must already have
the platform rights needed for the fixed resources; app users do not need them.
[Makers operations](https://learn.microsoft.com/en-us/connectors/powerappsforappmakers/),
[Flow permissions](https://learn.microsoft.com/en-us/connectors/flowmanagement/)

On add, persist pending access, apply the planned grants and read them back before
activating the new membership. On disable/remove, deny API access immediately,
then remove grants. A failed platform update leaves a visible pending/error
status and retryable command; it never restores revoked API access. Read all
relevant assignment pages. Remove only the identified assignment, never unrelated
permissions or the deployment owner's rights.

Before any platform mutation, the flow calls internal `AcquireSharingLease` with
`{plan_id, revision, execution_id}`. The server serializes each target across
both apps and returns `{lease_id, execution_id, sharing_plan}`. A newer removal
denies API access immediately but cannot start platform removal while an older
Add execution holds the lease. No timeout-based lease takeover is permitted.

Internal `RecordSharingResult` carries the plan ID/revision, lease ID/execution
ID, observed grants, safe error code and `external_calls_complete`. Completion
is true only when every issued platform mutation succeeded; non-issued actions
may be skipped. Failed or timed-out writes leave external outcome unknown and
retain the lease. Recovery requires proving the prior execution has stopped.
A completed superseded callback releases its own lease without activating stale
access or completing the newer plan. These internal operations are excluded from
the canvas operation allowlist. Tenant actions and the local store cannot share
a transaction, so partial completion remains explicit.

Management calls also use a durable global permit for their shared connection.
Internal `ReserveManagementCall` takes
`{plan_id, revision, lease_id, execution_id, step}` and returns
`{reservation_id, not_before}`. The step is one of the 16 fixed generated
Before/Add/Remove/Readback action names for the two app environments and two
membership branches. The flow waits until that UTC timestamp before calling
Management. `RecordManagementCall` repeats that identity with the reservation ID
and `outcome_known`; only Succeeded or non-issued Skipped actions establish a
known result. Confirmed completion releases the permit and starts a 13-second
cooldown. Failed/TimedOut calls retain it for host recovery, including failed
reads. The sharing execution cannot close while it holds this permit.

Reservations require a current plan and its running lease. Completion accepts
the original owning execution even after plan supersession. A busy reservation
creates no permit and makes the dependent action skip; the sharing command stays
pending for retry. A completed step cannot reserve again. Both pacing operations
are excluded from canvas. Keep the management connection dedicated to these
flows. If pacing exceeds the app response window, retain the original command
and recover through its recorded status; a response timeout does not prove the
flow stopped.

The September 24 tenant connector metadata confirms `body/put` and `body/delete`
for Makers, and `permissions/put` and `permissions/delete` for flow management.
Makers accepts the string `NotifyShareTargetOption: DoNotNotify`; `Notify` requests email. Do not send mail,
add a notification action or assume a Boolean `sendEmail` field exists.
[Notification contract](https://learn.microsoft.com/en-us/connectors/powerappsforadmins/#edit-app-role-assignment-as-admin)

## 6. Flow and canvas deployment sequence

1. Resolve the tenant and six directory identities, pin the two owners, and
   preserve existing app backups. No guessed account IDs or email-based fallback.
2. Add the broker operation to the existing connector and deploy disabled flows
   in the existing solution. Fix each flow's environment and broker connection.
3. Set Office 365 Users to invoker-owned; broker/directory/management connections
   remain private and flow-owned. Inspect the saved/exported connection sources
   and verify them using a second user with only view/run rights.
4. Enable secure inputs/outputs on every trigger/action carrying source text,
   replacement credentials or secret-bearing results. Verify actual run history.
5. Replace all direct canvas business calls with broker flow calls. Preserve
   review-command UUIDs, receipt handling, pagination and uncertain outcomes.
   Disable automatic retries of non-idempotent intake submission in the flow.
6. Add configuration and user screens. Authorize navigation from GetCurrentUser
   capabilities independently of `varEnvironmentReady`; only business actions
   depend on ready=true. Display permission-sharing failures as pending access.
7. Deploy server enforcement, verify legacy Basic cannot bypass it, then publish
   and accept both apps. An old published app may be denied during cutover; never
   reopen the bypass to conceal that mismatch.

Existing managed Entra SSO is reused. September 24 realm discovery returned
`Managed` for the corporate domain; no AD FS deployment is required.
This scope does not establish a new identity provider or collect work passwords.

## 7. Required acceptance evidence

- Actual invoker differs from the flow owner; the API and audit identify the
  invoker. Forged actor fields, raw headers, unknown tenant/ID and direct Basic
  calls fail. A removed member loses access on the next operation.
- Both pinned owners survive all delete/demote/disable attempts. Admins can
  configure runtime and manage Admin/Operator access; Operators cannot.
- Add/remove reconciles app and flow grants without mail or edit rights; simulate
  one-side failure and retry without duplicate grants or restored revoked access.
- Prod administration opens while Prod is disabled. Wrong-profile draft/apply,
  stale revision, expired test receipt, failed drain and restart recovery pass.
- Existing intake commit receipts, unknown submission, review replay/conflict,
  canonical padding and retained owner-requested records remain intact.
- Source/export review finds no secrets; actual run-history inspection confirms
  masking. App publication alone is not acceptance of these controls.

Record implementation, automated results and native tenant observations
separately. Current Azure SQL acceptance and the independent Prod target remain
outside this identity change; no legacy shipment handoff is introduced.

The administrator SOP contains a draft request for optional user-facing HTTPS
redirect names and a separate internal API hostname at the later VM move. No
DNS, redirect or SSO-provider configuration was performed for this increment.
